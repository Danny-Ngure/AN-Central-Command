# @an/db

Drizzle schema, migrations, and seed scripts for the AN Central Command Postgres+PostGIS database.

## Layout

```
packages/db/
├── drizzle.config.ts         # drizzle-kit config (reads DATABASE_URL from .env.local)
├── src/
│   ├── client.ts             # drizzle client factory + setRequestContext() for RLS
│   ├── apply-extras.ts       # applies extras/*.sql (idempotent, tracked in _extras_applied)
│   ├── types/
│   │   └── geometry.ts       # PostGIS Point / Polygon / MultiPolygon custom types
│   └── schema/
│       ├── index.ts          # barrel — single import surface
│       ├── audit.ts          # append-only audit_log (NFR-050)
│       ├── geography.ts      # constituencies, wards, sub_locations, villages, polling_stations
│       ├── identity.ts       # people, auth_credentials, sessions
│       ├── community.ts      # community_leaders, community_sites, village_issues
│       ├── activities.ts     # activities, visits (append-only), meetings
│       ├── supporters.ts     # community_programs, committed_supporters, consent_log
│       └── election.ts       # station_reports (append-only), incidents
├── migrations/               # generated by `drizzle-kit generate` — DO NOT hand-edit
├── extras/                   # hand-written SQL — triggers, RLS, custom functions
│   ├── 01_append_only_triggers.sql   # NFR-050 — audit_log, visits, station_reports, consent_log
│   ├── 02_audit_triggers.sql         # AUTO-INSERT into audit_log on every write
│   └── ... (RLS policies, column encryption land here next)
└── README.md
```

## Workflow

```bash
# 1. Make sure docker compose is up (Postgres+PostGIS+pgcrypto+admin_audit role).
docker compose -f ../../infra/docker-compose.yml up -d

# 2. Copy .env.example to .env.local — drizzle.config.ts loads it automatically.
cp .env.example .env.local

# 3. Generate a migration from the current schema (after any schema/*.ts edit).
pnpm db:generate

# 4. Apply migrations + hand-written extras to the dev DB.
pnpm db:migrate:all          # = db:migrate + db:apply-extras

# 5. Inspect with Drizzle Studio (web UI on localhost:4983).
pnpm db:studio
```

## Migrations vs extras

| Path | Source | Applied by | When |
|---|---|---|---|
| `migrations/*.sql` | auto-generated by `drizzle-kit generate` from `schema/*.ts` | `pnpm db:migrate` | every schema change |
| `extras/*.sql` | hand-written | `pnpm db:apply-extras` (tracked in `_extras_applied` table) | triggers, RLS, custom functions |

Every `extras/*.sql` file must be **idempotent** (`CREATE OR REPLACE`, `DROP IF EXISTS`, `CREATE INDEX IF NOT EXISTS`). The tracking table skips already-applied files on re-run, but a forced re-run (drop the row from `_extras_applied`) must still succeed.

## Conventions

- **Every table** has `id uuid primary key` (server-default `gen_random_uuid()` for now; UUIDv7 in Phase 2c).
- **Every mutable table** has `created_at` / `updated_at` timestamps (`timestamptz`).
- **Geometry columns** use SRID 4326 (WGS-84). Spatial indexes use GiST.
- **Soft delete** by default — a nullable `deleted_at` column. Hard delete is reserved for DPA §26 erasure requests (anonymises PII rather than removing the row).
- **PII columns** that are flagged for column encryption are documented per-table; pgcrypto applied in a post-generate migration (Phase 2c).
- **RLS policies** live in `migrations/<NNNN>_rls_*.sql` files added by hand after each schema change. The schema does not encode policies — Drizzle's auto-generator doesn't produce them.
- **Audit triggers** live in `migrations/<NNNN>_triggers_audit_*.sql`. Every writable table gets an INSERT/UPDATE/DELETE trigger that writes to `audit_log`.

## Things this package deliberately does NOT do

- **No application logic.** Just the schema, the client factory, and seed scripts.
- **No business rules.** Constraints encoded in the database (check constraints, NOT NULL, RLS) are fair game; conditional logic belongs in the API.
- **No backend framework integration.** `apps/web` imports `db` and `setRequestContext` from `@an/db` and uses them in Next.js route handlers.

## How RLS works in this codebase

- **Migrations / seeds / ad-hoc psql**: connect as the DB owner (`alfayo` in dev). Superuser bypasses RLS automatically — no policy applies.
- **Application**: same connection, but every transaction begins with `setRequestContext()` which executes `SET LOCAL ROLE app_user; SET LOCAL app.role = '<role>'; SET LOCAL app.ward_id = '...'; SET LOCAL app.person_id = '...'`. Dropping into `app_user` (no BYPASSRLS) makes policies apply for the rest of the transaction. The session vars feed the helper functions (`rls_role()`, `rls_ward_id()`, `rls_person_id()`) referenced by every policy predicate.
- **Verifying RLS as a non-superuser** in psql: `SET ROLE app_user; SET app.role = 'canvasser'; SET app.person_id = '00000000-0000-0000-0000-000000000001'; SELECT * FROM committed_supporters;` — should return only supporters registered by that person.

**20 tables defined.** v2.0+ adds `opposition_candidates` and `opposition_assessments` for FR-072 (Current Race Intelligence with restricted strategic notes).
